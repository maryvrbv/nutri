# Нутри — сопровождение клиента специалистом

Первая версия сервиса по ТЗ: два связанных кабинета. Клиент с телефона видит план на день, отмечает приём и ведёт дневник. Специалист с компьютера составляет схемы приёма БАДов и видит достоверную историю приёма, анализов и самочувствия.

## Запуск

Нужен Node.js 22.12 или новее. Внешняя база не нужна: используется встроенный `node:sqlite`.

```bash
npm install
npm run build          # собрать веб-клиент
npm run seed -- --reset # демо-данные (необязательно)
npm start              # http://localhost:3000
```

Для разработки: `npm run dev` поднимает сервер на :3000 и Vite на :5173 с прокси на API.

Демо-аккаунты после `npm run seed`, пароль у всех `demo12345`:

| Кто | Почта | Что посмотреть |
|---|---|---|
| Специалист | `elena@demo.nutri` | Список клиентов, карточка Анны, конструктор схемы |
| Клиент | `anna@demo.nutri` | «Сегодня», схема с двумя версиями, динамика ферритина, дневник |
| Клиент | `dmitry@demo.nutri` | Документ с чужим ФИО — проверка принадлежности |

В `samples/` лежат два образца бланка в PDF: их можно загрузить, чтобы проверить распознавание.

Проверки: `npm test` (сквозные сценарии по критериям приёмки и модульные тесты) и `npm run typecheck`.

## Как устроено

```
server/src
  db.ts            схема SQLite и миграции
  core.ts          доступ, журнал изменений, уведомления, зашифрованное хранилище файлов
  auth.ts          регистрация, вход, сессии
  care.ts          приглашения, согласие, отзыв доступа, список клиентов, сводка
  schedule.ts      проверка схемы, расписание, сравнение версий (чистые функции)
  schemes.ts       черновик → публикация → версии → отмена курса
  intakes.ts       отметки о приёме, идемпотентность, история изменений
  adherence.ts     статистика выполнения и полноты
  labs.ts          документы, проверка распознавания, подтверждение, динамика
  recognition.ts   распознавание бланков (сменный модуль)
  reference.ts     справочник показателей, перевод единиц, автоматические пояснения
  reminders.ts     планировщик напоминаний и контрольных дат
  time.ts          часовые пояса без внешних библиотек
  app.ts           HTTP API
web/src
  client/          кабинет клиента (телефон): Сегодня, Схема, Анализы, Дневник, Ещё
  specialist/      кабинет специалиста (компьютер): клиенты, карточка, конструктор схемы
  shared/          анализы, график динамики, история приёма, общая шкала
```

### Ключевые решения

- **Версии схемы.** Каждая публикация — новая версия с датой вступления в силу. Неотмеченные будущие приёмы прошлой версии заменяются, отмеченные остаются привязаны к той позиции (дозировке, инструкции), которая действовала в момент приёма. Клиент видит, что изменилось и с какой даты.
- **Приёмы создаются при публикации** на весь курс (до 366 дней) в часовом поясе клиента. При смене пояса местное время приёмов сохраняется, момент напоминания пересчитывается.
- **Отметки.** Каждая позиция — отдельная запись. Повторное нажатие или повтор запроса после обрыва связи не создаёт дублей (`request_id`). Отметку задним числом можно внести и исправить: сохраняются время приёма, время записи и вся история.
- **Статистика.** Выполнение = принято / наступившие запланированные (без отменённых и будущих). Рядом — полнота отметок: отсутствие отметки не считается пропуском.
- **Анализы.** До подтверждения значения не попадают в динамику. Ручная правка сохраняет исходное распознанное значение и автора. Если ФИО в бланке не совпадает с владельцем профиля, результаты не добавляются, пока владелец не подтвердит, что документ его.
- **Три уровня информации:** данные лаборатории, автоматическое пояснение (явно подписано, с источником, версией справочника и входными данными, без диагнозов и назначений) и комментарий специалиста. Внутренние заметки специалиста клиенту не видны.
- **Единицы.** Результаты в разных единицах объединяются в один график только по проверенному правилу перевода. Иначе это отдельные ряды.
- **Уведомления.** В приложении и в браузере. На экране блокировки по умолчанию — нейтральный текст без названий добавок и результатов. Тихие часы переносят напоминание на их окончание. Отменённые приёмы напоминаний не создают.

### Безопасность и данные

- Доступ проверяется на сервере в каждом запросе. Специалист видит только клиентов с активным согласием; чужие данные отвечают 404.
- Пароли — scrypt. Сессия — httpOnly-cookie, защита от CSRF через обязательный служебный заголовок.
- Файлы анализов хранятся зашифрованными (AES-256-GCM, ключ `NUTRI_FILE_KEY`) и отдаются только через API с проверкой доступа.
- Журнал изменений схем, отметок, результатов и доступа (`audit_log`).
- В технический лог пишутся только метод, маршрут, код ответа и время: без тел запросов, параметров и медицинских данных.
- Экспорт всех данных пользователя (JSON) и удаление аккаунта с файлами — в настройках.
- Резервное копирование: база — один файл SQLite в режиме WAL, копируется `sqlite3 data/nutri.db ".backup backup.db"` или `node:sqlite` `backup()`. Каталог `data/files` копируется как есть (файлы уже зашифрованы). Ключ хранить отдельно от копий.

## Что нужно решить до работы с реальными данными

ТЗ (раздел 12) требует определить это до запуска — это решения владельца продукта, а не кода:

1. **Размещение.** Где хостится сервер и хранятся данные. Для пользователей из России персональные данные о здоровье — специальная категория (152-ФЗ): нужны локализация в РФ, согласие на обработку, уведомление Роскомнадзора. Для ОАЭ — свои требования (PDPL, медицинские данные — отдельно).
2. **Сроки хранения** документов, отметок и журнала после отзыва доступа и удаления аккаунта.
3. **Внешний OCR.** Встроенный распознаватель читает PDF с текстовым слоем (бланки из личных кабинетов лабораторий) и работает внутри сервиса. Фото и сканы требуют внешнего OCR — модуль `Recognizer` готов к подключению, но передача данных внешнему сервису должна быть согласована. Пока для фото пользователь вносит значения вручную.
4. **Справочник показателей** (`reference.ts`) — тексты пояснений нужно проверить медицинскому редактору. Источники сейчас — MedlinePlus (NIH) и NIH ODS.
5. **Каналы доставки** вне приложения (почта, push на телефон) — нужен провайдер; в первой версии работают уведомления в приложении и в браузере.

## Развёртывание

### Для себя на своих данных

Если сервисом пользуетесь только вы, это обработка данных для личных нужд: требования 152‑ФЗ к оператору на неё не распространяются. Но это ваши медицинские данные на публичном сервере, поэтому:

- в production регистрация закрыта: первый аккаунт создаётся свободно, остальные — только клиентами по ссылке-приглашению (`NUTRI_OPEN_REGISTRATION=0` по умолчанию);
- демо-данные (`npm run seed`) на этом сервере не запускать;
- сайт открывать только по HTTPS (Caddy ниже получает сертификат сам);
- ключ `NUTRI_FILE_KEY` хранить отдельно от резервных копий.

Порядок: создать аккаунт специалиста (первый), выпустить приглашение и по нему создать свой аккаунт клиента. Прошлые схемы вносятся с прошлыми датами — они сохраняются как завершённые и видны на графиках анализов.

Caddy перед сервисом (`/etc/caddy/Caddyfile`):

```
nutri.example.ru {
  reverse_proxy localhost:3000
}
```

Есть `Dockerfile`: каталог данных монтируется в `/data`, ключ передаётся через `NUTRI_FILE_KEY`. Нужен один процесс с постоянным диском — serverless-платформы вроде Vercel не подходят из-за SQLite и планировщика напоминаний.

```bash
docker build -t nutri .
docker run -p 3000:3000 -v nutri-data:/data -e NUTRI_FILE_KEY=$(openssl rand -base64 32) nutri
```

## Критерии приёмки → тесты

Все 12 критериев из раздела 13 ТЗ покрыты сценариями в `server/test/acceptance.test.ts`: приглашение и согласие, публикация схемы, расписание на сегодня и отметки, отметки у специалиста, неизменность истории при новой версии, загрузка и проверка анализа, динамика, разделение пояснения и комментария, уведомления, отзыв доступа, ручной ввод при ошибке распознавания, отсутствие напоминаний по отменённым приёмам.
